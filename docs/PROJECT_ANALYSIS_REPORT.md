# 프로젝트 분석 및 요구사항 비교 보고서

| 항목 | 내용 |
|---|---|
| 분석 기준일 | 2026-08-15 |
| 분석 대상 | 분석 당시 Git 추적 루트 프로젝트, `docs`, 미추적 `team-docs` 전체 |
| 비교 기준 | 기존 `docs/REQUIREMENTS.md`, `docs/TECHNICAL_DECISIONS.md`, 개인별 제안·구현안 |

## 1. 결론 요약

현재 루트 프로젝트는 **개발 환경과 공통 UI의 초기 골격만 있는 상태**다. Django 프로젝트와
6개 도메인 앱은 생성되어 있으나 모델, 업무 URL, 폼, 서비스, 관리자 등록, 인증 화면,
실제 업무 페이지는 구현되지 않았다. 기존 24개 MVP 요구사항 중 완전히 충족된 항목은 없고,
시스템 기반·인증 기반·Admin 기반만 일부 준비되어 있다.

분석 당시 `team-docs`에는 회원·포털, 회차, 팀 편성, 팀 평가, 결과에 관한 상세 제안이
있었으나 다음과 같은 이유로 현재 구현으로 볼 수 없었다.

- 디렉터리 전체가 Git에서 추적되지 않는 `?? team-docs/` 상태다.
- 대부분 기획 문서·목업이며 루트 Django 설정과 URL에 연결되지 않았다.
- 안중섭 디렉터리의 실행 코드도 루트 앱이 아니라 개인 폴더 안의 별도 복제 프로젝트다.
- 개인 문서끼리 제출 수정, 팀 편성 시작 방식, 결과 누락 처리 등 핵심 정책이 충돌한다.

따라서 개인 산출물을 그대로 합치는 방식은 안전하지 않다. 이번 통합본은 루트 합의 문서를
우선하고, 개인 제안은 충돌하지 않는 상세만 채택했다.

개인별 초안 디렉터리는 통합 완료 후 제거했다. 비교 결과와 채택·기각 근거는 이 보고서에
보존한다. 이후 범위 재검토 결과인
`REFINED-REQUIREMENTS.md` v1.4가 현재 유일한 구현 기준이며, 과제 업로드는 MVP에서 제외되고
팀 편성은 자동 초기 배치 후 같은 화면에서 수동 조정하는 단일 흐름으로 확정되었다. 팀·개인
평가는 공통 `reviews` 저장 구조를, 팀·개인 결과는 공통 `EvaluationResult`를 사용한다.

## 2. 현재 프로젝트 분석

### 2.1 구성 현황

| 영역 | 현재 상태 | 판정 |
|---|---|---|
| 기술 스택 | Django 5.2, PostgreSQL, dotenv, Bootstrap 5.3 의존성과 설정 존재 | 일부 준비 |
| 앱 구조 | `accounts`, `rounds`, `teams`, `team_reviews`, `peer_reviews`, `results` 등록 | 골격만 존재 |
| 데이터 모델 | 루트 앱에 `models.py`와 업무 migration 없음 | 미구현 |
| URL | 홈과 Django Admin만 연결 | 미구현 |
| 인증 | Django Auth 의존성·미들웨어는 있으나 로그인/로그아웃 URL·템플릿·역할 정책 없음 | 일부 준비 |
| 관리자 | `/admin/`은 있으나 업무 모델·등록이 없음 | 일부 준비 |
| UI | `base.html`, 준비 완료 홈 카드, 최소 CSS만 존재 | 프로토타입 |
| 테스트 | 홈 200 응답과 제목 확인 1건 | 매우 부족 |
| CI/품질 도구 | Ruff, djLint, pre-commit 설정과 GitHub Actions 이력 존재 | 설정됨 |
| 업무 기능 | 회차·팀·평가·결과 기능 모두 루트에는 없음 | 미구현 |

현재 홈 문구도 “기본 개발 환경이 준비되었습니다”이므로 서비스 화면이 아니라 초기화 완료
확인 페이지에 해당한다. `base.html`도 `LAYOUT.md`가 정의한 사이드바·상단 바·모바일
내비게이션을 아직 구현하지 않았다.

### 2.3 실행 및 품질 검사

다음 검사를 시도했으나 환경에 Django와 개발 도구가 설치되지 않아 실행하지 못했다.

```text
python manage.py check
→ ModuleNotFoundError: No module named 'django'

ruff, djlint
→ 실행 파일 없음
```

따라서 코드가 설정상 실행 가능한지는 정적 검토만 했으며, DB 연결·테스트·린트 통과를
확인하지 못했다.

## 3. 개인별 산출물 요약

분석 당시 `team-docs`는 합의 문서가 아니라 개인별 사고 결과로 평가했다.

| 작성자 | 주요 범위 | 유용한 제안 | 통합 시 주의점 |
|---|---|---|---|
| 우동현 | 회원, 학생 대시보드, 마이페이지, 튜터 관리, 피드백 | 역할별 IA, 평가 카드 상태·정렬, 현재 행동 중심 대시보드 | 화이트리스트 승인·온보딩·알림·레이더 차트는 기존 MVP 밖이며 REST API/SPA식 경로도 현재 스택과 다름 |
| 안중섭 | 회차, 템플릿, 실시간 팀별 평가 개시, 개인 평가, 코드·ERD | 회차 상태, 문항 유형, 마감 경고, 템플릿 개념 | 리뷰 모델을 `rounds`가 소유하고 보안 검증이 빠진 별도 데모 구현이며 루트와 연결되지 않음 |
| 양성용 | 팀 편성, 자동편성 알고리즘, 상태·저장·예외 | 회차별 팀 모델, 원자적 저장, 무시드 처리, 표준편차·반복 조합 최소화, 동시 수정 방지 | 초기 문서와 최종안이 충돌했으나 정제 v1.4에서 자동 초기 배치+수동 조정으로 확정 |
| 노희주 | 팀 평가 상세 PRD | 대상별 진행률, 필수 항목 검증, 이탈 경고, 마감 경계 | 별도 최종 제출·부분 평가 전체 미반영·제출 전 수정 정책이 기존 중복 제출 금지와 충돌 |
| 최성호 | 결과·순위·공개·다음 편성 | 4개 공개 토글, 수동 채점, 공동순위, 3회차 가중 시드, 관리자/학생 화면 | 무응답을 0점 처리하면 실제 점수와 결측이 섞이며 재채점 후 공개 정책이 미정 |

개인 평가를 독립적으로 상세화한 개인 PRD는 없다. 안중섭의 회차 데모에 개인 평가 폼이
포함되어 있지만 개인 평가의 요구사항·권한·테스트 기준을 대체하지 못한다.
초기 통합본에서도 이를 `동료 평가`라는 이름으로만 표시해 별도 기능이 없는 것처럼 보이는
문제가 있었다. 통합 요구사항과 플로우에서는 기존 요구사항 명칭인 `개인 평가`를 복원하고
대상·제출·권한·진행률·예외 흐름을 별도 항목으로 상세화하되, 저장은 팀 평가와 공통
`reviews` 테이블을 사용하도록 정리했다.

## 4. 주요 불일치와 통합 결정

### 4.1 정책 충돌표

| 주제 | 서로 다른 제안 | 통합 결정 | 이유 |
|---|---|---|---|
| 제품 범위 | 반복 프로젝트 평가 vs 주차별 튜터링·공지·피드백·역량 분석 | 반복 프로젝트 평가 MVP로 제한 | 기존 루트 요구사항 우선 |
| 로그인 | Django Auth 우선 vs Google OAuth·가입 승인·온보딩 동시 구현 | 비밀번호+Django 세션과 사전 등록 계정용 Google OIDC만 MVP | 로그인 편의는 포함하되 공개 가입·승인 흐름은 제외 |
| 프런트 방식 | Django Template vs `/api/...` 기반 SPA식 인터페이스 | Django Template 서버 렌더링 | 기술 결정과 현재 구조 우선 |
| 표준 용어 | 개인 평가, 팀원 평가, 피어 리뷰, 동료 평가 혼용 | UI·문서에서 `개인 평가` 사용, 정의에서 동료 평가임을 명시 | 기존 요구사항 명칭을 유지하면서 자기 평가와 혼동을 방지 |
| 회차 제어 | 회차 전체 기간으로 개방 vs 발표 팀별 `RoundTeamSlot` 개방 | MVP는 회차 상태·기간으로 일괄 제어 | 기존 요구사항에 슬롯이 없고 복잡도 증가 |
| 과제 지원 | 과제 안내·결과물 업로드 포함 vs 평가 운영만 포함 | 과제·파일·링크 제출은 MVP 제외 | MVP는 평가 데이터와 팀 운영에 집중 |
| 팀 편성 시작 | 수동·자동 별도 기능 vs 자동 배치 뒤 수동 조정 | 자동 초기 배치와 한 화면의 수동 조정 | 하나의 저장 모델로 같은 목적을 달성 |
| 팀 자동편성 | 고득점자 우선 고정 vs 전원 무작위 후 표준편차 개선 | 후자 채택 | 편향을 덜 고정하고 품질 측정 가능 |
| 편성 데이터 저장 | 방식·후보·확정 상태 저장 vs 최종 구성만 저장 | `Team`·`TeamMembership`만 저장 | 자동·수동은 편집 동작이지 업무 상태가 아님 |
| 수동 조정 균형 | 불균형 경고·강제 vs 불균형 허용·무경고 | 허용하되 저장 전 지표 표시 | 관리자 재량과 실수 방지를 함께 확보 |
| 팀 평가 제출 | 즉시 수정 불가 vs 종료 전 덮어쓰기 vs 전체 최종 제출 전 수정 | 대상별 1회 제출, 제출 후 수정 불가 | 루트 기술 결정의 재제출 차단과 단순한 무결성 우선 |
| 임시 저장 | 필수 항목 일부 서버 저장 vs 별도 상태 없음 | MVP 서버 임시 저장 제외 | 상태·집계 복잡도와 부분 데이터 혼동 방지 |
| 전체 최종 제출 | 전체 완료 후 일괄 확정, 미완료면 전부 미반영 vs 대상별 제출 즉시 유효 | 별도 전체 최종 제출 제외 | 기존 요구사항에 없고 제출 손실 위험이 큼 |
| 문항 저장 | 동적 템플릿·문항 vs `score1`, `score2` 고정 필드 | 재사용 질문 템플릿과 문항별 응답 구조 | 회차의 템플릿 선택 요구 충족 |
| 앱 소유권 | `rounds` 소유 vs 팀·개인별 앱 분리 vs 공통 리뷰 앱 | 공통 `reviews` 앱이 두 유형의 제출·답변 소유 | 동일 생명주기와 제약 중복 제거 |
| 팀 소속 범위 | 전역 Team/TeamMember vs 회차별 Team/TeamMembership | 모든 팀 소속은 회차에 귀속 | 과거 회차와 현재 회차 혼합 방지 |
| 평가 후 팀 변경 | 진행 중 수정 허용 vs 평가 대상은 확정 팀 기준 | 평가 데이터 생성 후 팀 변경 차단 | 대상 자격과 점수 귀속 보존 |
| 결과 공개 | 단일 `is_result_visible` vs 4개 독립 토글 | 4개 독립 토글 | 기존 요구사항의 항목별 공개를 구체화 |
| 무응답 점수 | 0.00점과 경고 vs 미정 | `N/A`, 순위·시드 제외 | 1~5점 척도에서 0은 유효 점수가 아니며 결측과 성과를 분리해야 함 |
| 채점 시점 | 종료 후 자동 암시 vs 관리자 수동 채점 | 종료 후 수동 채점·검토 | 운영자가 공개 전 이상치를 확인할 수 있음 |
| 재채점 | 공개 유지/비공개 전환 미정 | 원자적 재계산 후 전체 비공개 | 공개 결과가 고지 없이 바뀌는 문제 방지 |
| 동점 순위 | 미정 vs 공동순위 | 경쟁 순위(`1, 2, 2, 4`) | 개인 결과안의 명시적 정책 채택 |
| 시드 | 단순 누적/최종점수 vs 최근 3회 20·30·50 | 최근 최대 3개 유효 점수 가중평균 | 최신 성과 반영과 과거 완충을 동시에 제공 |
| 소셜·알림·차트 | 개인 PRD의 핵심 범위 vs 기존 MVP 제외 | 후속 범위 | 선행 평가 핵심 기능이 아직 없음 |

### 4.2 같은 개인 문서 내부의 충돌

양성용의 `flow.md`는 최초 수동 분류와 임시저장을 제안하지만,
`teams_design_and_senarios.md`는 자동 배치 뒤 관리자 수정을 제안한다. 정제 요구사항 v1.4는
자동 초기 배치와 수동 조정을 하나의 편집 흐름으로 통합하고, 최종 팀 구성 외 방식·후보 상태는
저장하지 않는 것으로 확정했다.

안중섭의 `CONTEXT.md`와 ADR은 회차 종료 전 평가 덮어쓰기를 허용하지만 루트
`TECHNICAL_DECISIONS.md`는 이미 제출한 평가의 재제출을 서버에서 차단하도록 한다. 별도
합의 근거가 없으므로 루트 정책을 유지했다.

최성호 문서는 재채점의 멱등성, 공개 상태, 신입생 시드, 팀 편성 버튼 소유권을 미정으로
남긴다. 통합본은 재채점 시 비공개 전환, N/A 회차 제외, `results → teams` 서비스 호출로
기능 경계를 정했다.

## 5. 개인 구현안의 코드 수준 위험

당시 `team-docs/안중섭`의 코드는 요구사항을 이해하기 위한 데모로만 평가했으며, 아래 위험
때문에 루트 프로젝트로 병합하지 않았다.

| 위험 | 코드에서 확인한 형태 | 영향 |
|---|---|---|
| 인증 우회 | `StudentProfile.objects.first()`를 로그인 학생으로 사용 | 모든 사용자가 첫 학생으로 평가 가능 |
| 권한 누락 | 튜터·학생 뷰에 로그인/역할 검사 없음 | 직접 URL로 관리자 종료 가능 |
| 대상 검증 누락 | POST의 팀·학생 ID를 그대로 `update_or_create` | 자기 팀·자기 자신·다른 팀 평가 가능 |
| 점수 검증 누락 | 문자열을 `int`로 바꾸고 저장, 1~5 제약 없음 | 범위 밖 점수·서버 오류 가능 |
| 기간 검증 누락 | `COMPLETED`만 확인 | 시작 전·마감 후 제출 가능 |
| 소유권 혼합 | TeamReview·PeerReview가 `rounds/models.py`에 존재 | 전용 앱 경계 붕괴, 병합 충돌 증가 |
| 고정 문항 | 동적 템플릿이 있어도 모델·폼은 `score1`, `score2` | 문항 추가·유형 변경 불가 |
| 회차 없는 팀 | Team과 TeamMember가 회차를 참조하지 않음 | 반복 회차의 팀 이력과 대상 판정이 섞임 |
| 잘못된 미제출 계산 | 학생 수 × 열린 팀 수에서 제출 수만 차감 | 자기 팀 제외가 반영되지 않아 수치 과대 가능 |
| 최신 회차 추정 | 단순 `order_by('-id').first()` | DRAFT나 종료 회차를 현재 회차로 오인 |
| 종료 전제 누락 | `current_round`가 없을 때 POST·조회 방어 부족 | 빈 DB에서 예외 가능 |
| 기본 5점 선택 | 새 폼이 5점으로 미리 선택됨 | 무의식적 최고점 제출 편향 |

개인 코드의 migration과 템플릿도 루트 migration history에 속하지 않는다. 모델을 통합할 때는
루트 앱별로 새 migration을 만들고 제약·권한 테스트를 먼저 작성해야 한다.

## 6. 통합 후 권장 구현 순서

| 단계 | 범위 | 선행 이유 |
|---|---|---|
| 1 | accounts 역할·학생 식별 정보, 로그인/로그아웃, 보호 라우팅 | 모든 업무의 사용자와 권한 기반 |
| 2 | rounds 회차·참가자·TEAM/PEER 템플릿·문항, Admin | 팀과 평가가 참조할 기준 데이터 |
| 3 | teams 회차별 팀·팀원, 자동 초기 배치와 수동 조정 | 평가 대상 자격의 기준 |
| 4 | reviews 공통 제출·답변과 TEAM·PEER 대상·기간 검증 | 두 평가 유형의 공통 입력 기반 |
| 5 | 제출 현황과 회차 종료 경고 | 채점 전 데이터 완결성 확인 |
| 6 | results 공통 결과·N/A·공동순위·재채점 | 평가 원천 데이터 이후 구현 |
| 7 | 공개 설정·학생 결과·시드·다음 회차 연결 | 계산 결과가 안정된 뒤 공개 |
| 8 | 공통 대시보드·반응형 셸·접근성 보강 | 기능 흐름 통합 |
| 9 | 후속 인증·피드백·통계 기능 재기획 | MVP 완료 이후 |

각 단계는 모델·migration·Admin·서비스·뷰·템플릿·정상/예외 테스트를 함께 완료해야 한다.

## 7. 남은 제품 결정과 권고

통합본은 구현 가능한 기본값을 정했지만 다음 항목은 실제 개발 착수 전에 제품 책임자의
승인을 권장한다.

- 평가 제출 후 수정 불가 정책과 서버 임시저장 제외
- 평가 데이터 생성 후 팀 변경 차단
- 무응답을 0점이 아닌 N/A로 처리하고 순위·시드에서 제외
- 재채점 시 모든 공개 항목 자동 비공개
- 시드의 최근 3회 20%·30%·50% 가중 방식
- 발표 팀별 실시간 개방 기능을 MVP에서 제외

승인 후에는 이 결정을 `TECHNICAL_DECISIONS.md` 또는 ADR에 옮겨 요구사항과 기술 기준의
불일치를 없애야 한다.
