## 1. 문서 목적과 적용 원칙

이 문서는 저장소의 기존 요구사항과 당시 `team-docs`에 있던 개인별 제안을 합친 분석 당시
통합본이다. 개인별 초안 디렉터리는 최종 문서 통합 후 제거되었다.
현재 기능 구현과 인수 테스트의 유일한 규범 문서는
[`REFINED-REQUIREMENTS.md`](REFINED-REQUIREMENTS.md)이며, 충돌 시 이 문서를 사용하지 않는다.

상충하는 내용은 다음 순서로 결정했다.

1. 저장소 루트의 기존 요구사항과 기술 결정
2. 데이터 무결성, 권한, 평가 공정성
3. 여러 개인 문서에서 공통으로 제안한 내용
4. 한 개인 문서에만 있는 상세안

개인 제안이 기존 MVP 범위를 넓히는 경우에는 향후 범위로 분리했다. 충돌의 원문과 결정
근거는 [프로젝트 분석 및 요구사항 비교 보고서](PROJECT_ANALYSIS_REPORT.md)에 기록한다.

## 2. 제품 목표와 범위

AX 평가 시스템은 반복되는 학생 프로젝트 평가를 다음 순서로 운영하는 Django 기반 웹
서비스다.

```text
수강생 관리
→ 평가 회차·과제 생성
→ 팀 편성
→ 팀 발표 및 평가
→ 개인 평가
→ 점수·순위 계산
→ 결과 공개
→ 시드 계산
→ 다음 회차 팀 편성
```

### 2.1 MVP 포함 범위

- Django Auth 기반 로그인과 역할별 접근 제어
- 수강생 등록·조회·수정·활성 상태 관리
- 회차, 과제, 기간, 상태, 팀 수, 평가 템플릿 관리
- 독립적인 수동 팀 편성과 시드 기반 자동 팀 편성
- 다른 팀 평가와 같은 팀 구성원 간 개인 평가
- 제출 현황과 미제출자 확인
- 팀 점수, 개인 점수, 최종점수, 공동순위 계산
- 항목별 결과 공개
- 다음 회차 편성용 시드 계산
- Django Admin을 이용한 관리자 CRUD

### 2.2 MVP 제외 범위

- Google/Kakao 등 소셜 로그인
- 화이트리스트 가입 승인, 승인 대기·거절, 강제 온보딩
- 공지사항, 이메일·푸시·실시간 알림
- 레이더 차트, 역량 강·약점 자동 분석, 통계 그래프
- 튜터 피드백 작성과 통합 피드백 모달
- Excel 다운로드, 평가 이력 버전 관리, 팀 변경 감사 로그
- REST API 전용 프런트엔드 또는 별도 SPA

위 항목은 MVP 완료 후 별도 요구사항과 개인정보·익명성 정책을 합의한 뒤 추진한다.

## 3. 용어와 역할

| 용어 | 정의 |
|---|---|
| 평가 회차 | 하나의 과제, 팀 편성, 평가 기간, 결과를 묶는 운영 단위 |
| 팀 평가 | 수강생이 본인 팀을 제외한 다른 팀의 발표·산출물을 평가하는 행위 |
| 개인 평가(동료 평가) | 수강생이 같은 팀의 다른 구성원을 대상으로 기여도·협업 등을 평가하는 행위 |
| 평가 템플릿 | 같은 평가 유형의 문항을 묶은 재사용 가능한 질문지 |
| 팀 점수 | 다른 팀 수강생에게 받은 유효한 팀 평가 점수의 평균 |
| 개인 점수 | 같은 팀 구성원에게 받은 유효한 개인 평가 점수의 평균 |
| 최종점수 | `팀 점수 × 40% + 개인 점수 × 60%` |
| 시드 점수 | 다음 회차 자동 팀 편성의 성적 균형 기준값 |
| 수강생 | 본인 팀·과제 확인, 평가 제출, 공개된 본인 결과 조회가 가능한 사용자 |
| 튜터/관리자 | 수강생·회차·팀·평가·결과의 전체 운영 권한을 가진 사용자 |

문서와 UI에서는 기존 요구사항의 명칭인 **개인 평가**를 표준 용어로 사용한다. 이는 자기
평가가 아니라 같은 팀 구성원이 서로를 평가하는 동료 평가이며, 코드 앱명은 기존 경계에 따라
`peer_reviews`를 유지한다.

## 4. 기능 요구사항

### 4.1 시스템, 인증, 권한

| ID | 요구사항 | 우선순위 | 인수 기준 |
|---|---|---|---|
| SYS-001 | 시스템은 Django 5.2와 PostgreSQL 기반 서버 렌더링 웹 애플리케이션으로 구현한다. | 필수 | 개발·테스트 환경에서 Django 시스템 검사가 통과하고 PostgreSQL 설정으로 실행된다. |
| SYS-002 | 사용자·수강생·회차·팀·평가 템플릿·결과의 기본 CRUD에는 Django Admin을 활용한다. | 필수 | 각 업무 모델이 Admin에 등록되고 역할에 맞는 조회·편집 권한이 적용된다. |
| AUTH-001 | 모든 업무 화면은 로그인한 사용자만 접근할 수 있다. | 필수 | 비로그인 직접 URL 요청은 로그인 화면으로 이동한다. |
| AUTH-002 | MVP 로그인은 Django Auth의 ID/비밀번호 방식을 사용한다. | 필수 | 유효한 계정은 로그인되고 잘못된 자격 증명은 거부된다. |
| AUTH-003 | 사용자는 수강생과 튜터/관리자 역할로 구분한다. | 필수 | 서버가 역할을 검사하고 역할별 시작 화면과 허용 기능을 다르게 제공한다. |
| AUTH-004 | 수강생의 관리자 기능 접근과 다른 사용자의 개인 결과 접근을 서버에서 차단한다. | 필수 | 메뉴 숨김과 무관하게 직접 URL·POST 요청이 403 또는 안전한 화면으로 처리된다. |
| AUTH-005 | 로그인 사용자는 로그아웃할 수 있다. | 필수 | 세션 종료 후 보호 화면에 다시 접근할 수 없다. |

### 4.2 수강생 관리와 학생 홈

| ID | 요구사항 | 우선순위 | 인수 기준 |
|---|---|---|---|
| ACC-001 | 관리자는 수강생 계정과 기본 정보를 등록·조회·수정할 수 있다. | 필수 | Django Admin에서 CRUD가 가능하다. |
| ACC-002 | 관리자는 수강생의 활성·참여 상태를 관리한다. | 필수 | 비활성 수강생은 새 회차 편성 및 평가 대상에서 제외된다. |
| ACC-003 | 학생 홈은 현재 회차, 과제, 기간, 소속 팀, 팀·개인 평가 진행률을 요약한다. | 필수 | 진행 회차가 있으면 최신 상태가 표시된다. |
| ACC-004 | 진행 중인 회차가 없거나 팀이 확정되지 않은 경우 빈 상태 안내를 표시한다. | 필수 | 존재하지 않는 데이터를 임의로 대체하지 않는다. |
| ACC-005 | 학생 홈은 미완료 평가를 마감 임박순으로 우선 표시하고 해당 평가 화면으로 연결한다. | 권장 | 미완료, 완료, 마감·미제출 상태가 텍스트로 구분된다. |

### 4.3 평가 회차, 과제, 템플릿

| ID | 요구사항 | 우선순위 | 인수 기준 |
|---|---|---|---|
| RND-001 | 관리자는 회차명, 과제명·설명, 시작·종료 일시, 목표 팀 수를 관리한다. | 필수 | 생성·조회·수정이 가능하고 시작 시각은 종료 시각보다 이르다. |
| RND-002 | 회차 상태는 `DRAFT → IN_PROGRESS → COMPLETED` 순서로 전이한다. | 필수 | 역방향 전이와 종료 회차 수정은 거부된다. |
| RND-003 | `DRAFT`에서는 설정·팀 편성을, `IN_PROGRESS`에서는 평가 제출과 제한된 운영 수정을, `COMPLETED`에서는 조회·채점만 허용한다. | 필수 | 평가 데이터가 생긴 뒤에는 팀을 바꿀 수 없으며 UI와 서버가 같은 상태 규칙을 적용한다. |
| RND-004 | 시작·종료 일시도 평가 제출 가능 여부에 적용한다. | 필수 | 상태가 진행 중이어도 기간 밖의 제출·수정은 거부된다. |
| RND-005 | 관리자는 회차별 팀 평가 및 개인 평가 템플릿을 지정한다. | 필수 | 각 회차에 두 유형의 템플릿이 연결된다. |
| RND-006 | 템플릿에는 순서, 문구, 유형, 필수 여부가 있는 문항을 여러 개 등록한다. | 필수 | 문항 순서대로 동적 폼이 생성된다. |
| RND-007 | MVP 문항은 1~5점 척도형과 선택적 자유 서술형을 지원한다. | 필수 | 척도형은 정수 1~5만 저장되고 범위 밖 값은 서버에서 거부된다. |
| RND-008 | 회차 종료 시 미제출 현황을 경고하되 튜터가 확인 후 종료할 수 있다. | 권장 | 미제출 대상 수와 학생을 확인한 뒤 종료 여부를 다시 결정한다. |

MVP에는 발표 팀별로 폼을 실시간 개방하는 `RoundTeamSlot` 개념을 넣지 않는다. 모든 팀
평가는 회차의 기간과 상태로 함께 제어한다.

### 4.4 팀 편성 및 팀 조회

| ID | 요구사항 | 우선순위 | 인수 기준 |
|---|---|---|---|
| TEAM-001 | 관리자는 회차별 편성 대상과 팀 수를 지정하고 처음부터 수동 편성할 수 있다. | 필수 | 자동 편성을 거치지 않고도 모든 대상자를 배치·확정할 수 있다. |
| TEAM-002 | 관리자는 시드 점수를 이용해 자동 편성 후보를 생성할 수 있다. | 필수 | 후보 생성만으로 확정 팀 데이터가 바뀌지 않는다. |
| TEAM-003 | 자동 편성은 팀별 인원 차이를 최대 1명으로 유지한다. | 필수 | 학생 수가 나누어떨어지지 않는 경우에도 차이가 1명을 넘지 않는다. |
| TEAM-004 | 자동 편성은 유효한 시드가 있는 학생을 기준으로 팀 평균의 편차를 줄인다. | 필수 | 자동 편성 전후 비교에서 목적 함수가 악화되지 않는다. |
| TEAM-005 | 시드가 없는 학생은 0점으로 간주하지 않고 남은 정원에 무작위로 균등 배치한다. | 필수 | 전원 무시드인 첫 회차도 균등 무작위 편성이 된다. |
| TEAM-006 | 성적 균형을 악화시키지 않는 범위에서 직전 회차의 동일 조합을 줄인다. | 권장 | 제거할 수 없는 반복 조합은 오류가 아니라 검토 정보로 표시한다. |
| TEAM-007 | 관리자는 수동·자동 후보를 확정 전에 수정하고 자동 후보를 다시 생성할 수 있다. | 필수 | 학생 이동 후 중복·누락을 검사하고 확정 전에는 학생에게 공개하지 않는다. |
| TEAM-008 | 확정은 팀과 팀원 관계를 하나의 트랜잭션으로 저장한다. | 필수 | 일부만 저장되는 상태가 없고 학생은 같은 회차에 한 팀에만 속한다. |
| TEAM-009 | 진행 중 회차의 확정 팀은 관리자가 수정할 수 있고 종료 회차는 읽기 전용이다. | 필수 | 변경 적용 전 학생은 기존 확정본을 보고, 적용 성공 후 새 확정본을 본다. |
| TEAM-010 | 수강생은 현재 회차의 본인 팀과 팀원을 조회한다. | 필수 | 다른 회차나 다른 팀의 비공개 편성안이 섞이지 않는다. |

자동 편성 알고리즘의 기본 목적 함수는 유효한 팀 평균의 모집단 표준편차다. 구현은 개선
교환이 없거나 100회에 도달하면 종료할 수 있다. 수동 조정 결과의 인원 불균형은 허용하되
확정 전에 팀별 인원 차이를 관리자가 확인할 수 있어야 한다.

### 4.5 팀 평가

| ID | 요구사항 | 우선순위 | 인수 기준 |
|---|---|---|---|
| TR-001 | 수강생은 현재 회차에서 본인 팀을 제외한 모든 확정 팀을 평가 대상으로 본다. | 필수 | 본인 팀은 목록과 제출 대상에서 제외된다. |
| TR-002 | 대상 팀별로 현재 회차의 팀 평가 문항에 응답한다. | 필수 | 필수 문항을 모두 입력해야 제출할 수 있다. |
| TR-003 | 동일 회차·평가자·대상 팀 조합에는 평가 레코드가 최대 한 건만 존재한다. | 필수 | DB 유니크 제약과 서버 검증이 중복 생성을 막는다. |
| TR-004 | 제출 완료된 대상 팀 평가는 수강생이 다시 제출하거나 수정할 수 없다. | 필수 | 재전송·직접 POST도 차단되고 기존 값이 바뀌지 않는다. |
| TR-005 | 회차가 진행 중이고 기간 안일 때만 제출할 수 있다. | 필수 | 시작 전, 마감 후, 종료 후 요청은 저장되지 않는다. |
| TR-006 | 제출 후 목록에서 완료·미완료 상태와 전체 진행률을 확인한다. | 필수 | 저장된 유효 평가를 기준으로 상태를 계산한다. |

팀별 임시 저장, 제출 후 수정, 모든 팀 평가를 묶는 별도 최종 제출은 MVP에서 제외한다.
필요하면 제출 전 브라우저 입력 보존만 제공할 수 있으나 서버의 평가 상태로 간주하지 않는다.

### 4.6 개인 평가(팀 내 동료 평가)

개인 평가는 수강생이 자신의 점수를 입력하는 자기 평가가 아니다. 현재 회차에서 확정된 같은
팀의 다른 구성원을 한 명씩 평가하는 기능이다.

| ID | 요구사항 | 우선순위 | 인수 기준 |
|---|---|---|---|
| PR-001 | 수강생은 현재 회차의 같은 팀 구성원 중 본인을 제외한 사람만 평가한다. | 필수 | 본인과 다른 팀 학생은 목록과 제출 대상에서 제외된다. |
| PR-002 | 대상자별로 현재 회차의 개인 평가 문항에 응답한다. | 필수 | 필수 척도형 문항을 모두 입력해야 제출할 수 있다. |
| PR-003 | 동일 회차·평가자·대상 수강생 조합에는 평가 레코드가 최대 한 건만 존재한다. | 필수 | DB 유니크 제약과 서버 검증이 중복 생성을 막는다. |
| PR-004 | 제출 완료된 개인 평가는 수강생이 다시 제출하거나 수정할 수 없다. | 필수 | 재전송·직접 POST도 차단되고 기존 값이 바뀌지 않는다. |
| PR-005 | 회차가 진행 중이고 기간 안일 때만 제출할 수 있다. | 필수 | 시작 전, 마감 후, 종료 후 요청은 저장되지 않는다. |
| PR-006 | 대상자별 완료·미완료 상태와 전체 진행률을 확인한다. | 필수 | 본인을 제외한 확정 팀원 수를 분모로 계산한다. |
| PR-007 | 개인 평가의 척도형 문항은 필수이며 자유 서술형 의견은 문항 설정에 따라 선택 또는 필수로 동작한다. | 필수 | 문항의 필수 여부를 서버와 화면이 동일하게 검증한다. |
| PR-008 | 평가 대상이 없는 경우 이를 정상적인 완료 상태로 처리한다. | 필수 | 1인 팀은 `평가 대상 없음`을 표시하고 미제출자로 집계하지 않는다. |
| PR-009 | 학생은 제출 후 본인이 작성한 응답을 읽기 전용으로 확인할 수 있지만 다른 학생이 작성한 응답과 작성자 정보는 볼 수 없다. | 필수 | URL 조작으로 다른 평가자의 응답에 접근할 수 없다. |

개인 평가의 화면 흐름은 다음과 같다.

```text
개인 평가 목록
→ 같은 팀의 다른 구성원과 제출 상태 확인
→ 미완료 대상 선택
→ 대상자와 문항 확인
→ 1~5점 및 서술 의견 입력
→ 필수값·대상·기간·중복 검증
→ 제출 확인
→ 평가 응답 저장
→ 목록으로 돌아가 진행률 갱신
```

자기 자신과 다른 팀 학생은 화면 목록에서 제외할 뿐 아니라 직접 URL과 변조된 POST에서도
차단한다. 개인 평가 결과는 평가 대상자가 받은 유효한 제출 점수의 평균으로 계산하며,
구체적인 집계·N/A·공개 규칙은 4.8절을 따른다.

### 4.7 제출 현황과 평가 데이터

| ID | 요구사항 | 우선순위 | 인수 기준 |
|---|---|---|---|
| SUB-001 | 수강생은 팀·개인 평가의 대상별 제출 상태를 한 화면에서 확인한다. | 필수 | 미완료 대상을 선택하면 해당 폼으로 이동한다. |
| SUB-002 | 튜터는 회차별 전체 제출 건수와 미제출 학생·대상을 확인한다. | 필수 | 본인 팀·본인을 분모에서 제외한 정확한 기대 건수를 사용한다. |
| SUB-003 | 평가 응답은 문항별로 저장해 템플릿 변경과 문항 수 증가를 지원한다. | 필수 | 고정된 `score1`, `score2` 필드에 의존하지 않는다. |
| SUB-004 | 평가 시점의 확정 팀 소속을 기준으로 대상 자격을 검증한다. | 필수 | 팀 변경 때문에 이미 제출된 평가의 대상 의미가 바뀌지 않도록 평가 시작 후 팀 변경 정책을 일관되게 적용한다. |

평가가 시작된 뒤 팀 구성을 바꾸면 평가 자격과 집계가 달라질 수 있다. 따라서 평가 데이터가
한 건이라도 존재하는 회차의 팀 변경은 기본적으로 차단한다. 꼭 필요한 운영 수정은 기존 평가를
정리한 뒤 다시 시작하는 별도 관리자 절차로 처리한다.

### 4.8 점수, 순위, 공개, 시드

| ID | 요구사항 | 우선순위 | 인수 기준 |
|---|---|---|---|
| RES-001 | 팀 점수는 대상 팀이 받은 유효한 척도형 응답의 평균으로 계산한다. | 필수 | 본인 팀 평가와 무효·중복 응답은 포함하지 않는다. |
| RES-002 | 개인 점수는 대상 수강생이 같은 팀 동료에게 받은 유효한 척도형 응답의 평균으로 계산한다. | 필수 | 자기 평가와 다른 팀 평가를 포함하지 않는다. |
| RES-003 | 모든 원점수는 문항별 만점 차이가 있어도 5점 척도로 정규화한 뒤 소수점 이하 충분한 정밀도로 계산한다. | 필수 | 화면에는 소수 둘째 자리까지 반올림해 표시한다. |
| RES-004 | 최종점수는 `팀 점수 × 0.4 + 개인 점수 × 0.6`으로 계산한다. | 필수 | 같은 입력을 다시 계산해도 같은 결과가 나온다. |
| RES-005 | 팀 순위는 팀 점수, 개인 순위는 최종점수 내림차순의 경쟁 순위 방식으로 계산한다. | 필수 | 동점은 같은 순위이며 다음 순위는 동점자 수만큼 건너뛴다. |
| RES-006 | 유효 응답을 한 건도 받지 못한 구성 점수는 `0점`이 아니라 `산출 불가(N/A)`로 처리한다. | 필수 | 실제 최저점과 데이터 부족을 구분하고 최종점수·순위·시드에서 제외한다. |
| RES-007 | 튜터는 종료 회차에서 채점을 수동 실행하고 공개 전 전체 결과를 검토한다. | 필수 | 채점 전 학생 화면은 집계 대기 상태를 표시한다. |
| RES-008 | 채점 재실행은 기존 산출물을 원자적으로 갱신하고 모든 학생 공개 플래그를 비공개로 되돌린다. | 필수 | 공개 점수가 조용히 바뀌지 않고 튜터가 다시 검토·공개한다. |
| RES-009 | 튜터는 `팀 1위`, `전체 팀 순위`, `본인 최종점수`, `본인 개인 순위`를 회차별로 각각 공개한다. | 필수 | 학생은 공개된 항목만 보고 관리자는 항상 전체를 본다. |
| RES-010 | 학생은 본인의 공개된 개인 결과와 공개된 팀 단위 결과만 조회한다. | 필수 | 다른 학생의 개인 점수·순위 상세에는 접근할 수 없다. |
| RES-011 | 다음 회차 시드는 최근 최대 3개 유효 최종점수에 오래된 순서대로 20%·30%·50% 가중치를 적용한다. | 필수 | 1~2개 회차만 있으면 사용 가능한 최신 쪽 가중치를 재정규화하고 N/A 회차는 제외한다. |
| RES-012 | 시드 계산과 자동 팀 편성은 결과 공개 여부와 무관하게 튜터만 실행한다. | 필수 | 시드 값은 학생 화면에 노출하지 않는다. |
| RES-013 | 자유 서술형 평가 응답은 MVP에서 튜터/관리자만 조회한다. | 필수 | 학생에게 작성자나 원문을 노출하지 않으며 학생 피드백 공개는 후속 익명성 정책으로 분리한다. |

점수 계산 순서는 다음과 같이 고정한다.

1. 각 척도형 응답을 5점 척도로 정규화한다. 자유 서술형은 점수에서 제외한다.
2. 한 평가자가 한 대상에게 제출한 척도형 문항을 동일 가중 평균해 제출 점수를 만든다.
3. 대상이 받은 유효한 제출 점수를 평가자별 동일 가중 평균해 팀 점수 또는 개인 점수를 만든다.
4. 중간 계산은 `Decimal` 정밀도를 유지하고, 공개 점수는 `ROUND_HALF_UP`으로 소수 둘째
   자리까지 반올림한다.
5. 순위와 동점 판정은 학생에게 표시되는 소수 둘째 자리 점수를 기준으로 한다.

## 7. 역할별 완료 조건

### 수강생

```text
로그인
→ 학생 홈에서 현재 회차 확인
→ 본인 팀·과제 확인
→ 다른 팀 평가
→ 같은 팀 구성원 개인 평가
→ 제출 현황 확인
→ 공개된 결과 확인
```

- 본인에게 허용된 대상만 한 번 평가할 수 있다.
- 마감·종료·중복 요청으로 기존 데이터가 바뀌지 않는다.
- 공개되지 않은 점수와 다른 학생의 개인 결과를 볼 수 없다.

### 튜터/관리자

```text
수강생 관리
→ 회차·과제·템플릿 생성
→ 수동 또는 자동 팀 편성·확정
→ 평가 시작·제출 현황 확인·종료
→ 채점·검토
→ 항목별 결과 공개
→ 시드 계산
→ 다음 회차 편성
```

- 운영 흐름의 각 단계가 이전 단계의 완료 조건을 서버에서 확인한다.
- 종료·채점·재공개처럼 결과에 영향을 주는 행동은 확인 절차를 거친다.
- 관리자 공개 설정과 무관하게 전체 결과를 검토할 수 있다.

상세 기능 및 페이지 전이는 [기능 및 페이지별 플로우](FLOWS.md)를 따른다.
